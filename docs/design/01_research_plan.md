## 1. Objective、motivation 与 goals

### 1.1 总体 objective

设计并验证一个面向大规模有状态算法评估的 CPU/GPU 执行系统：在固定 GP-ACO 程序语义、搜索预算和数值模式下，降低整代评估及完整训练的时间，并解释其随程序结构、外层批量和内层问题规模变化的性能。

设第 $g$ 代程序集合为 $\mathcal P_g$，训练实例集合为 $\mathcal B_g$，随机重复集合为 $\mathcal R$。一个逻辑评估任务是

$$
e=(p,b,r),\qquad
F(p)=\operatorname{Aggregate}_{b,r}\bigl[Q(\operatorname{Run}(p,x_b,\xi_r))\bigr].
$$

主要优化目标为

$$
\min_\theta T_{\mathrm{generation}}(\mathcal P_g,\mathcal B_g,\mathcal R;\theta),
$$

其中 $\theta$ 是执行计划，不是 ACO 或 GP 的搜索超参数。执行计划必须满足内存预算、任务完整性和已冻结的算法语义。

完整训练的次级目标是降低 $T_{\mathrm{training}}$。GPU kernel 时间、吞吐和硬件计数器用于解释该目标，不替代该目标。

### 1.2 Motivation A：AAD 的评估成本限制了可使用的设计预算

每个候选算法都需要在问题实例和随机重复上运行。增加候选数量、训练实例数、随机重复数或进化代数，都会扩大评估工作量。AutoPSO 已展示 GPU 上的双层算法设计，EvoX 和 EvoGP 已提供进化计算及程序种群的 GPU 执行能力；因此，本研究不能以“首次使用 GPU 进行大规模候选算法评估”为动机。[R05] [R07] [R08]

本研究要回答的是：现有执行边界是否使特征生成、程序求值和内层状态维护之间仍存在可消除的工作；消除这些工作并优化硬件执行后，新增预算用于搜索广度还是评价可靠性更有效。

### 1.3 Motivation B：短程序可以触发昂贵的输入特征计算

当前十个终端不只是对距离和信息素的直接读取。部分终端需要候选集合上的统计归约、动态排名、对数或几何计算。树节点数不能完整描述评估成本。[R01] [R02]

研究假设：以“生成终端所需的计算 + 树求值 + 分数变换”为联合优化对象，比只编译 GP 树更有效。是否成立，以及收益在哪些程序上成立，由 E03—E05 验证。

### 1.4 Motivation C：外层规模与内层规模产生不同的硬件压力

增加 $P,B,R$ 通常增加独立任务；增加城市数 $n$ 则同时延长构造链并扩大单任务状态。对于密集信息素矩阵，状态量按 $n^2$ 增长。它们不是同一种“规模扩展”。

团队曾观察到 TSP500 训练加速不如 TSP100 明显。本计划将其记为 **U01：团队报告、待按历史版本复核**，不把它视为已测得的新结果。需要分离问题规模、程序分布、有效工作量、计时边界和硬件资源的影响。

### 1.5 Goals 与完成证据

| Goal | 要达到什么 | 完成证据 | 不接受的替代证据 |
|---|---|---|---|
| G1 工作负载理解 | 明确各阶段成本及其扩展规律 | 冻结种群重放、真实训练时间线、硬件计数器、受控干预 | 仅 GPU 利用率截图 |
| G2 计算重写 | 减少终端与表达式的重复工作 | 相同状态上的功能测试、工作量统计、CPU/GPU 两端收益 | 删除昂贵终端后更快 |
| G3 CPU 加速 | 改善已有优化 CPU 实现 | 对 Numba FP32 基线的端到端比较、SIMD/缓存/负载证据 | 只与 Python 标量实现比较 |
| G4 GPU 加速 | 改善整代完成时间 | 对当前 CUDA 单树版和张量版的比较，包含编译与调度成本 | 只报告最佳 warm kernel |
| G5 规模解释 | 解释 TSP100/500 差异并验证适应策略 | 规模分解、干预实验、未见负载上的计划选择结果 | 从显存占用小推断计算受限 |
| G6 AAD 价值 | 判断更多算力是否改善算法设计 | 等墙钟预算、独立测试、完整质量—时间曲线 | 更大种群的个别最好结果 |
| G7 适用边界 | 确定可迁移和不可迁移部分 | 跨变体、跨硬件；可选的第二类内层设计任务 | 只更换外层搜索器就宣称普适 |

不预先承诺 10×、100× 等加速倍数。方法是否保留依据可重复的端到端收益和适用范围，而不是目标倍数。

## 2. 研究叙事与贡献边界

### 2.1 论文主线

AAD 需要评估大量候选算法。已有进化框架和 GPU 求解器解决了多层并行的一部分问题，但 GP-ACO 中候选程序结构、终端生成和搜索状态共同决定成本。固定的程序求值接口和固定的任务配置可能不能覆盖这种差异。我们构建联合计算表示，先减少必要工作，再分别针对 CPU 局部性和 GPU 整代吞吐组织执行，最后研究其性能边界和算法设计价值。

“可能不能覆盖”是待验证的问题，不是对所有已有框架的断言。外部组合基线可以消除部分差距；这本身就是需要接受的结果。

### 2.2 预设 contributions

| 编号 | 拟贡献 | 对应方法 | 最低证据要求 |
|---|---|---|---|
| C1 | 面向有状态候选算法评估的特征—程序联合优化 | M1 | 不止终端掩码裁剪；至少展示联合生成与生命周期处理的独立收益 |
| C2 | 面向种群评估的局部性和向量化 CPU 后端 | M2 | 对现有 Numba FP32 强基线有效；明确收益机制 |
| C3 | 程序资源与搜索状态规模感知的 GPU 执行计划 | M3 | 对最佳固定计划有效，计入选择开销，并在未见负载上验证 |
| C4 | 外层/内层扩展、TSP500 瓶颈和等时间 AAD 价值的系统研究 | E01—E13 | 受控归因、完整训练、独立测试和失败区间 |

C2 只有在形成可复用执行设计时才独立成项；若仅是常规移植，则合并到系统实现。C3 若不能优于简单固定策略，则不包装为“自适应方法”，保留性能区间分析并缩减方法主张。

### 2.3 不作为独立创新的内容

单树、FP32、批处理、候选并行、数据驻留、CUDA JIT、CPU 多线程、普通 SIMD、前缀扫描、通用公共子表达式消除，以及已有 `required_mask` 都不是单独的新贡献。相关先例见技术证据表。[R02] [R03] [R05] [R07] [R09] [R11]

不宣称修改后的运行与所有历史 GP-ACO 实现一致。只要求本研究比较组之间使用同一算法合同。

<a id="workload"></a>
## 3. 固定的 GP-ACO 工作负载

### 3.1 函数集与数值合同

$$
\mathcal F=\{\mathrm{ADD,SUB,MUL,PDIV,NEG,MIN,MAX,ABS}\}.
$$

沿用当前保护除法

$$
\operatorname{PDIV}(a,b)=\frac{ab}{b^2+10^{-6}},
$$

以及逐 primitive 的非有限值处理和 $[-10,10]$ 裁剪。保留 $-1,-0.5,0,0.5,1$ 与当前 ERC 机制。[R01]

实现时将数值常量、树参数、工作区、分数、路径长度和适应度归约显式设为 FP32。整数索引、位集和计数器随机数可以使用整数类型；这不构成 FP64 搜索。检查 CPU 隐式浮点提升，不只检查输入数组 dtype。

FP32 主模式不启用不受控的快速数学重关联；FMA、数学库和编译选项逐后端记录。`fast-math` 单独作为质量—速度扩展实验。数值正确性检查在开发和离线实验中进行，不插入正式计时路径。

### 3.2 终端依赖与有效范围

| 终端 | 关键依赖 | 可共享或外提的部分 | 不能做的事情 |
|---|---|---|---|
| RTau | 当前候选边信息素、可行集合上的 log-tau 均值和标准差 | 同一步共享统计量；合适条件下复用原始 log-tau | 跨 visited 状态缓存整个终端 |
| REta | 静态启发值、当前可行集合统计 | 静态 log-eta；同一步共享均值/标准差 | 将 REta 整体当成静态特征 |
| BaseConf | 基础 ACO 分数、当前候选总分、候选数 | 共享基础总分和 log-count | 缓存全局归一化概率后忽略当前可行集合 |
| DistRank | 距离顺序与当前可行掩码 | 静态顺序；当前掩码的一次扫描 | 用静态排名替代可行集合内排名 |
| Entropy | 当前候选基础分布 | 每一步一次归约并广播 | 为每个候选重复计算整个熵 |
| ConstructProg | 当前构造步骤、n | 同一步广播 | 跨不同构造步骤复用 |
| ACOProg | 当前 ACO 迭代、迭代预算 | 任务迭代级外提 | 混用不同任务/预算的值 |
| Stagnation | 当前任务的停滞状态 | 状态变化时更新 | 跨候选算法共享停滞量 |
| MutualRank | 静态双向近邻排名、n | 实例级静态计算或按需读取 | 为每个程序复制静态全矩阵 |
| TurnCos | 前一城市、当前城市、候选城市、坐标 | 当前入边向量和范数每一步一次 | 将三点角度视为只依赖一条静态边 |

该表依据当前 CUDA 定义，精确公式和边界行为在 P0 导出为机器可读合同。[R02] 合同导出是实现验收工作，不是重新选择终端。

### 3.3 单树接入与 ACO 变体

主协议采用当前有界残差接入：

$$
s_{ij}=s^{\mathrm{base}}_{ij}\bigl(1+\gamma\tanh(f_p(z_{ij}))\bigr),
\qquad \gamma=1/3.
$$

`gamma=1/3`、`candidate_size=20`、32 只蚂蚁、500 次 ACO 迭代来自当前纯 TSP100 配置，作为首轮默认值；新研究将 dtype 改为 FP32 并只训练转移树。[R02] [R04]

保留 AS、同步 ACS、MMAS 的固定信息素更新规则。AS 作为首个实现入口；主性能实验覆盖三种变体。同步 ACS 的局部更新可见性必须单独测试。不得为了融合而移动其同步边界。

主实验关闭局部搜索，避免混入另一类工作负载。局部搜索只在扩展实验中开启，并为所有比较组提供相同规则。

### 3.4 默认规模与外层配置

| 项目 | 默认值 | 用途 |
|---|---:|---|
| 种群 P | 100 | 主工作点 |
| 每代实例 B | 32 | 主工作点；实例 schedule 冻结 |
| 训练随机重复 R | 1 | 主性能点；在预算分配实验单独增加 |
| 蚂蚁 A | 32 | 不按 n 自动改变 |
| ACO 迭代 I | 500 | 主工作点 |
| 候选表 K | 20 | 耗尽后的 fallback 规则固定 |
| GP 代数 G | 50 | 固定工作量完整训练 |
| 树上限 | 31 节点、深度 5 | 单树上限；不把原双树预算重新分摊 |
| 初始深度 | 2—4 | 沿用当前配置 |
| 交叉/变异/复制 | 0.80 / 0.15 / 0.05 | 正式后端比较保持相同 |
| 精英/锦标赛 | 10 / 4 | 沿用当前配置 |
| 核心训练规模 | n=100 与 n=500 分开训练 | 不混合成一个难以归因的平均值 |

除“单树、FP32、移除在线审计”外，默认值尽量沿用当前配置。[R04] 若更大 P 的敏感性实验涉及完整进化，精英数采用固定 10% 比例并在实验标识中区分；冻结种群性能实验不涉及该变化。

执行补充v1.1明确适应度为标签gap%的均值：$100(L-L^*)/L^*$，不使用ACO结果作为分母。固定ACO仅作为性能对照，采用共享规范FP32后端缓存结果，独立记录生成成本并供所有后端共享；不使用测试结果作为训练参考。

训练中的验证仍可在 FP32 下选择候选，不设 CPU FP64 复评或自动回退。验证、候选选择与正常 checkpoint 的时间包含在完整训练计时中。

## 4. 具体挑战与待检验缺口

| 挑战 | 当前代码或工作负载证据 | 不能直接推出的结论 | 本研究的解决路径 |
|---|---|---|---|
| 输入特征可能比树算术昂贵 | 终端包含动态统计、排名和几何函数 [R02] | 所有程序都受特征计算限制 | M1 依赖图、联合生成、按终端类别实验 |
| 代码已有优化，弱对照会夸大新收益 | 现有 CPU 已 njit、实例局部性、标量广播；GPU 已 tiled 与生成式求值 [R02] [R03] | 新系统必然显著更快 | 保留强基线和分层消融 |
| 程序结构与终端成本异构 | 变长树与不同 required masks [R01] [R03] | 分桶一定降低寄存器或尾部成本 | M3 编译资源检查、分桶代价测量 |
| 活跃搜索状态可能影响并发和局部性 | 每逻辑任务有独立信息素和蚂蚁状态 | 显存容量充足就无访存瓶颈 | M3 状态分块、访存和并发度实验 |
| 新程序不断产生 | 外层 GP 持续变异和交叉 | warm JIT 收益可以代表完整训练 | M1 编译摊销、结构缓存、E04/E09 |
| 大 n 与大 P 是不同扩展 | 构造链与状态规模的增长规律不同 | 大 n 必然提升 GPU 相对收益 | E06 分开扫描 P/B/R 与 n |
| 浮点和随机运行会改变闭环工作量 | 路径选择影响后续状态和 fallback | 相同 seed 就保证相同轨迹 | 状态重放与完整闭环两层比较 |
| 通用 GPU-GP 接口可能保留中间物化 | 待通过外部组合基线验证 | EvoGP 或 EvoX 必然无法融合 | 接入试验、接口成本单独计量 |

## 5. Method 总体设计

本方法包含三个模块，使用同一个工作负载描述。

```text
GP 种群 + 实例 schedule + 随机重复
                  |
                  v
M1 特征—程序依赖图 / 数值合同 / 程序成本特征
                  |
          +-------+-------+
          |               |
          v               v
M2 CPU 执行计划      M3 GPU 执行计划
原生求值、SIMD、      资源分组、状态分块、
二维任务分块          候选并行与融合选择
          |               |
          +-------+-------+
                  |
                  v
按逻辑任务汇总 FP32 适应度 -> 完成整代 -> 外层进化
```

这是一套面向“可描述的数值规则 + 可访问的内层搜索状态”的执行系统，不是任意 Python 程序的自动 GPU 编译器。

### 5.1 统一接口

```text
ProgramSpec:
  typed_ast, fp32_constants, semantic_hash, structural_hash
  required_features, dependency_graph, live_value_estimate

ProblemSpec:
  instance_id, n, coordinates, distance_convention
  static_arrays, candidate_order, static_memory_bytes

TaskSpec:
  task_id, program_id, instance_id, repeat_id
  algorithm_variant, search_budget, rng_namespace

ExecutionPlan:
  backend, program_group, instance_tile, repeat_tile
  active_task_limit, candidate_lanes, kernel_family
  materialization_policy, compile_policy, workspace_plan

EvaluationResult:
  task_id, fp32_fitness, status, optional_final_tour
```

`task_id` 与物理线程和任务排序无关。外层进化只读取完成规定工作后的结果，不采用“先完成者先繁殖”。

## 6. M1：特征—程序联合优化

### 6.1 中间表示

将候选集合、公共统计、终端生成、树表达式和分数变换纳入同一有向无环计算图。每个节点记录：

| 属性 | 含义 |
|---|---|
| `dependencies` | 静态几何、信息素、visited、当前/前一城市、迭代状态等 |
| `scope` | 实例、任务迭代、蚂蚁步骤、候选 |
| `read_set/write_epoch` | 读取的状态及其版本；决定缓存何时失效 |
| `shape` | 标量、候选向量或静态边表 |
| `numeric_contract` | FP32 运算、裁剪、保护除法和非有限值行为 |
| `estimated_work/bytes` | 计算和物化的估计代价 |
| `users` | 哪些终端/表达式复用当前值 |

静态数据可跨程序共享。动态节点只有在依赖状态相同时才能复用。程序结构相同只允许共享代码，不自动允许共享中间结果或适应度。

### 6.2 变换顺序

1. 从输出分数反向求依赖闭包；基础分数、候选选择等宿主逻辑需要的量不能被误删。
2. 合并同一作用范围内相同的公共统计与纯表达式。
3. 将仅依赖迭代状态或步骤标量的子表达式外提；不改变逐算子裁剪位置。
4. 对动态排名等具有专门结构的计算选择等义算法。
5. 根据复用次数和字节代价决定直接重算、寄存器/局部暂存或数组物化。
6. 将所需终端、树和分数变换生成到同一 CPU/GPU 求值段。
7. 计算活跃值和编译资源信息，提供给后端计划器。

禁止跨裁剪边界的代数重关联。例如，`clip(clip(a+b)+c)` 不能改成 `clip(a+b+c)`。可以调整纯子树的执行先后以降低活跃值，但必须保留操作数方向、每个节点的运算及其保护行为。

### 6.3 动态 DistRank 的等义重写

当前 CUDA 的候选路径反复统计前序未访问候选；fallback 路径对每个候选再次扫描全部城市。[R02]

对当前城市 i，预存按“实际使用的 FP32 距离、城市编号”排序的城市序列 $\pi_i$。设

$$
v_\ell=\mathbf 1[\pi_i(\ell)\text{ 在当前候选集合可行}],
\qquad
r_\ell=\sum_{q<\ell}v_q.
$$

则可行候选的动态排名为 $r_\ell$，由它生成当前定义的 DistRank。正常候选表用 K 长扫描；fallback 使用 n 长扫描或对已压缩可行集合执行等义排名。

在每个候选只求值一次的情况下，原候选排名总工作最坏为 $O(K^2)$，fallback 为 $O(mn)$，m 为当前未访问候选数。掩码扫描分别为 $O(K)$、$O(n)$。这只是排名子过程的复杂度，不是整条 tour 的复杂度。

CPU 采用紧凑掩码/前缀计数；GPU 比较子 warp 掩码、块级扫描和分块扫描。候选 K=20 时常数开销可能抵消收益；m 很小时的压缩比较也可能更便宜，需实测。

必须保留：距离平局规则、候选集合、候选输出次序、m=1 行为和 fallback 条件。全排序预处理的 $O(n^2\log n)$ 工作及 $O(n^2)$ 存储独立计时；已有排名表能够复用时记录节省，但不能假设预处理免费。

验证：E00 检验等义；E03 比较工作量与局部时间；E06 检查是否解释 TSP500 差异。

### 6.4 统计量与几何量的计算组织

对 RTau、REta、BaseConf、Entropy，生成其依赖闭包，只计算真正需要的统计量；共享候选遍历中的基础边量。不默认所有统计都合并为一遍，因为稳定的方差计算与额外寄存器可能改变收益。

TurnCos 的入边向量和范数可按步骤计算一次，候选仅计算出边相关部分。几何结果是否进一步缓存，依据缓存字节量、复用次数及访问方式选择。

不预计算完整的所有终端张量，也不把整个动态单树输出默认缓存成转移矩阵。当前终端集的可行集合依赖使这种整体缓存通常不成立。

### 6.5 编译与代码缓存

比较三条路径：现有紧凑解释器、只生成树表达式、联合生成特征—树代码。

代码缓存分两种键：

- **语义键**：完整树、FP32 常数位模式、数值合同、相关配置；用于精确区分程序。
- **结构键**：算子结构、终端位置、常数参数槽、数值合同、目标硬件和执行配置；用于复用常数参数化代码。

仅 ERC 变化时可尝试结构缓存，但运行时常数读取会妨碍部分常数折叠。E04 决定这种交换是否划算。

粗略的专门化条件为

$$
H\,(t_{\mathrm{interp}}-t_{\mathrm{specialized}})>T_{\mathrm{compile}}+T_{\mathrm{plan}},
$$

H 是预计剩余调用量，不用未来世代的真实寿命作预测输入。可以依据本代预算和历史缓存统计估计；保留保守解释器回退。

编译优化和工作量减少有交互：减少树调用后，JIT 的摊销可能变差。因此必须联合测量，不把两个独立微基准的加速倍数相乘。

## 7. M2：CPU 执行后端

### 7.1 起点与新增工作

现有 CPU 已有 Numba 编译边界、实例优先的数据复用、标量终端广播以及向量列求值设计。新方法必须对这一基础做增量比较。[R03]

主实现路径：Python 保留外层实验控制；CPU 热路径使用可审计的原生循环。先将现有 Numba 后端完整改成 FP32，再引入 C++/编译生成的专门化求值器。只有在 E04/E05 显示收益时才保留复杂编译链。

### 7.2 候选分块与向量化

在小候选块中联合生成特征和树求值，减少解释栈读写。块宽依据 CPU 指令集、候选数量和活跃值选择，不固定要求所有机器使用同一 SIMD 宽度。

检查实际向量指令、向量宽度、标量数学函数调用和 gather 成本。数组循环不等于已经向量化；Intel 官方文档也区分向量化比例与实际向量长度。[R19]

长树不强求全部中间值驻留寄存器。候选分块、表达式调度和局部暂存之间做受控比较。

### 7.3 程序—实例二维任务分块

调度块为

$$
\text{instance tile}\times\text{program tile}\times\text{repeat tile}.
$$

实例优先有利于静态数据复用，程序优先有利于代码与分派局部性。根据 B、CPU 核数和程序成本选择块大小；避免只按实例分配而在 B 较小时留空闲核心。

每个工作线程使用私有工作区；跨任务复用容量，不保留前一任务的有效状态。比较静态划分、动态队列和局部窃取。调度粒度为整个评估任务或任务块，不在每个候选上创建任务。

多插槽系统记录线程绑定、首次触碰和 NUMA 访问。主图同时报告 1 核及全部物理核心，SMT 开关单独记录。CPU 与 GPU 比较时明确使用了多少 CPU 核、是否共享主机资源。

### 7.4 保留与退出条件

若专门化只改善求值器、不改善整代时间，则仅作为组件结果，不作为 CPU 主贡献。若二维调度在所有核心负载上均不优于现有实例优先布局，则保留简单布局，报告其适用性。

不因强 CPU 缩小 GPU 加速倍数而更换基线。CPU 与 GPU 都受益于同一工作量重写，是支持 M1 的结果。

## 8. M3：GPU 种群执行计划

### 8.1 优化对象与约束

计划变量包括：程序分组、实例分块、活跃任务数、候选 lanes、任务块映射、kernel 家族和中间值物化方式。

$$
\theta^*=\arg\min_{\theta\in\Theta_{\mathrm{feasible}}}
\widehat T_{\mathrm{generation}}(X,\theta).
$$

可行集必须满足：显存预算、block/thread 限制、共享内存限制、已验证的数值合同以及对应 ACO 变体的同步语义。

不以最大 occupancy 为目标。寄存器、活跃 warps 和访存都用于解释执行时间，不能各自独立最大化。[R16] [R18]

### 8.2 程序分组

分组特征为终端依赖、节点数、特殊函数数量、活跃值估计、字节码/生成代码大小，以及已编译配置的寄存器和 spill 信息。

先比较四个明确基线：不分组、仅按长度分组、按终端依赖分组、按资源估计分组。记录分组和额外 kernel/编译的成本。

同组内仍可能有多棵不同树。不声称“分桶消除所有分歧”；warp/sub-warp 内尽量处理同一程序是已有合理映射。真正要验证的是分组能否改善资源使用和尾部，而非只改变任务顺序。[R02] [R07]

### 8.3 状态分块与数据布局

数据分为三类：

| 类别 | 布局原则 | 复用边界 |
|---|---|---|
| 实例静态数据 | 以实例保存距离、坐标、候选表、静态顺序 | 跨程序与随机重复共享 |
| 独立任务状态 | 信息素、停滞量、最优解等按 task 保存 | 不跨任务共享搜索状态 |
| 蚂蚁/步骤状态 | visited、当前/前一城市、路径、临时统计 | 只在对应任务与蚂蚁范围内复用 |

删除只为信息素树计算的工作，但保留固定 ACO 更新仍需要的计数和缓冲。其删除收益先在所有“单树基线”中实现，不记成 M3 收益。

主要容量条件为

$$
M_{\mathrm{static}}+E_{\mathrm{active}}M_{\mathrm{task}}
+M_{\mathrm{workspace}}\le M_{\mathrm{budget}}.
$$

活跃任务数不等于整代任务数。通过任务波次处理控制状态工作集；每个任务在内层搜索期间留在设备上，不逐步骤在 CPU/GPU 间交换。

不默认压缩完整信息素矩阵为候选边矩阵：fallback 和固定更新可能需要非候选边。稀疏表示、延迟蒸发只作为后续扩展，并必须验证读取与更新语义。

### 8.4 并行映射和 kernel 家族

首轮实现有限选择集，而非一次实现所有 GPU 技术：

| 家族 | 定义 | 适用假设 |
|---|---|---|
| K1 固定 tiled | 继承现有单任务协作、候选子组映射 | 强基线 |
| K2 分组 tiled | 按程序资源分组，调整候选 lanes 与任务块 | 程序异构带来的资源浪费明显 |
| K3 状态分块 tiled | 在 K2 上限制活跃任务并调整实例局部性 | 大 n 或大 P 下工作集压力明显 |
| K4 长驻留/较深融合 | 减少重复启动或状态搬运 | 仅在时间线证明这些成本显著时实现 |

候选 lanes 首轮枚举 4、8、16、32。普通候选和 fallback 可以使用不同求值子过程，但不得改变任务逻辑或采样分布。

CUDA Graph 作为降低重复主机提交的工程选项，与核心方法分开消融。不将 Graph 的创建成本、首次实例化和编译成本隐去。[R17] [R18]

### 8.5 有限执行计划选择器

模型输入限定为当前已知信息：n、K、A、I、P/B/R、静态/任务字节数、程序特征、硬件配置和允许的历史运行统计。不得使用测试任务的最优配置或未来路径工作量作为输入。

第一版使用少量分区查找表或线性/树型回归预测整批时间，不优先开发复杂学习模型。训练数据来自独立 tuning 工作负载。评估时预测若干可行计划，选择预计最短者。

比较对象：全局最佳固定计划、按 n 固定计划、人工规则、受限穷举得到的离线 oracle。oracle 只作上界，不作为可以免费获得的运行时组件。

选择器评价用

$$
\operatorname{regret}(x)=
\frac{T_{\mathrm{selected}}(x)+T_{\mathrm{selection}}(x)}
{\min_{\theta\in\Theta}T_\theta(x)}-1.
$$

oracle 必须来自同一有限可行集。用独立重复估计所选最优配置的时间，减少“从噪声里挑最好”的偏差。

初始工程目标：留出集 median regret 不高于 10%，p90 不高于 25%，且相对最佳固定计划存在端到端收益。这些是预设目标，不是已得到的结果。跨架构分别报告“原模型零样本迁移”与“重新标定后迁移”，不能混称无需调优。

### 8.6 单代执行伪代码

```text
for generation in scheduled_generations:
    programs = get_population()
    descriptions = analyze_features_and_programs(programs)
    tasks = enumerate_logical_tasks(programs, instances, repeats)
    shortlist = propose_finite_plans(descriptions, tasks, hardware)
    code, resources = lookup_or_compile_within_budget(shortlist)
    plan = select_and_validate_plan(shortlist, resources, tasks)

    for task_tile in plan:
        initialize_task_state_fp32(task_tile)
        run_fixed_budget_search_fp32(task_tile, code, plan)
        write_results_by_logical_task_id(task_tile)

    wait_for_all_required_results()
    aggregate_fitness_fp32()
    perform_outer_selection_and_variation()
```

计划选择采用两步：先用 IR 和已知资源信息筛选少量候选；再检查实际编译资源，排除不可行配置并选定计划。只编译预算允许的候选，不在正式运行时免费穷举。若没有已编译的合适计划，使用可行的解释器或固定 kernel，并计入这条路径的成本。

可重排执行 tiles，但同一比较中的任务集合、随机命名空间和选择边界不变。

## 9. TSP100 到 TSP500：专项分析方案

### 9.1 分开计算量与状态量

在其他参数固定且多数步骤使用 K 长候选表时，候选评价主项近似为

$$
W_{\mathrm{candidate}}\propto PBRIAnK.
$$

密集信息素更新和存储分别包含 $PBRIn^2$、$PBRn^2$ 项。fallback 和 DistRank 另计，不塞入“常数”。

推导示例：P=100、B=32、R=1，仅 FP32 信息素矩阵在 n=100 时为 128 MB，在 n=500 时为 3.2 GB，按十进制字节计算；这是容量推导，不是实测显存峰值。实际峰值还取决于活跃任务数和工作区。

### 9.2 六个可区分假设

| 假设 | 预测观察 | 核心干预 | 被削弱的条件 |
|---|---|---|---|
| H4a 排名工作量增长 | fallback 排名比较数和对应时间增长 | 等义扫描替换 | 排名占比极小或替换不影响总时间 |
| H4b 工作集/局部性变化 | 每有效评价内存流量增大或等待增加 | 活跃状态及实例分块 | 分块在多点均无收益、流量不变 |
| H4c 资源阈值 | spill、资源限制或并发度出现拐点 | 改候选 lanes/融合粒度 | 资源变化与耗时不相关 |
| H4d 更新阶段主导 | 信息素更新时间增长更快 | 更新布局/并行配置 | 构造始终绝对主导 |
| H4e 程序分布变化 | TSP500 训练更常产生昂贵终端组合 | 同一冻结种群跨 n 重放 | 控制种群后仍出现相同差异 |
| H4f 计时或 CPU 分母变化 | 移除审计/编译边界差异后速度比变化 | 统一 FP32 端到端边界 | 统一后现象仍稳定存在 |

多个原因可能同时存在。先做单因素干预，再做必要的组合消融；不强行将总改善唯一分摊给一个机制。

### 9.3 两层证据

固定状态重放比较相同输入的组件工作量和时间；完整闭环运行检查收益能否转化为整代加速。前者隔离实现影响，后者包含真实路径和 fallback 分布。

跨 n 不能拥有逐元素相同的状态，因此使用相同程序 cohort、相同阶段分位和可行比例进行分层比较。诊断中不能仅以相同 seed 宣称两种后端执行了完全相同的搜索轨迹。

## 11. 适用范围和扩展任务

核心结论限于：可描述的单树数值规则、可访问的内层搜索状态、批量程序—实例评估，以及本计划测试的 CPU/GPU。

跨 AS/ACS/MMAS 证明不同状态更新结构下的适用性，不等于跨所有优化算法。更换 GP 外层为随机程序搜索或另一种进化选择，只证明评估器不绑定某一种外层策略。

若要以“通用 AAD 执行方法”为较强贡献，扩展一个不同内层任务。默认候选是 GP 调度规则设计：保留同类数值程序表示，新增调度特征和离散事件状态适配器。需单独调研其直接先行工作；已有 2026 年 GP 调度仿真加速预印本说明这一方向也不是空白。[R13]

扩展实验必须报告复用的模块、新增适配代码、不可复用的同步逻辑，以及端到端收益。若核心 GPU 方法在扩展中被重写为另一套专用实现，只能声称技术思路可借鉴，不能声称同一系统直接迁移。

多 GPU、FP8/FP16、Tensor Core、FPGA、复杂分布式通信和任意 Python AAD 不进入核心范围。DeepGEMM 与 MiMo 提供的是专门化、数据移动、状态生命周期及局部性/负载均衡的设计启示，不是可直接移植的 GP-ACO 加速器。[R14] [R15]

| P1 强基线与基线诊断 | 移植 CPU/GPU 已有优化、冻结 cohort、重现历史现象 | E01/E02 报告、状态快照、硬件清单 | 可以定位主要阶段；历史比较与新比较分开 |
| P2 共享计算优化 | 依赖图、排名扫描、公共统计和联合生成 | M1、E03/E04 | 功能通过，存在可解释的组件/整代收益 |
| P3 后端优化 | CPU 二维调度/SIMD；GPU 分组与状态分块 | M2/M3、E05—E07 | 强基线上有收益；回归区间有记录 |
| P4 计划选择与规模解释 | 有限选择器、留出评估、TSP500 干预 | E06/E08、模型和分析图 | 选择成本计入；无测试调参泄漏 |
| P5 完整训练与质量 | 固定工作量及等时间训练、测试最终路径 | E09—E11、最终质量表 | 计时完整、样本量冻结、独立测试完成 |
| P6 迁移和论文 | 跨变体/硬件，可选第二任务，复现材料 | E12/E13、最终证据矩阵 | 每项贡献有对应证据或已缩减 |

任何阶段均可否定某个优化，但不能通过降低强基线、隐藏回归点或改变数据划分来保留结论。

### 12.2 数据与结果管理

每条结果关联代码 commit、语义合同哈希、科学预算哈希、执行计划、程序 cohort、数据 manifest、随机命名空间、硬件清单及编译缓存状态。未完成、OOM、超时和功能失败都保留状态，不以缺行代替。

新文献和代码发现记入技术证据表。修改正式协议时创建新版本并说明影响，已运行数据不得重新标成预注册实验。

<a id="limitations"></a>
## 13. 风险与结果边界

| 风险 | 处理方式 | 对论文的影响 |
|---|---|---|
| 收益主要来自 DistRank 修复 | 将它作为独立通用优化；继续检验联合编译和计划器 | 不把一个局部修复包装成通用编译系统 |
| 当前终端掩码已消除大部分冗余 | 保留更简单实现，转向有证据的资源与状态问题 | 缩减 C1 |
| JIT 成本抵消运行收益 | 采用解释器/结构缓存，报告摊销边界 | 不只展示 warm 性能 |
| 最佳固定 GPU 配置足够好 | 保留固定策略，报告何时无需自适应 | 缩减 C3，保留规模分析 |
| 优化 CPU 与 GPU 性能接近 | 明确工作负载与硬件区间 | CPU 优化和边界结论仍有价值 |
| 速度提高但最终质量无改善 | 报告执行贡献及预算分配结果 | 不声称改善 AAD 质量 |
| FP32 后端质量差异明显 | 调查采样/更新/数学选项；报告速度—质量边界 | 不使用在线 FP64 修复来掩盖差异 |
| TSP500 现象不能在新协议重现 | 保留历史记录，说明协议或版本变化 | 不继续用旧现象证明新方法 |
| 第二任务无法复用核心模块 | 限定为 GP-ACO 深入案例 | 不使用通用 AAD 的过强标题 |

---

## 14. 论文和复现材料的最低集合

论文至少包含：工作负载与计时定义、联合计算方法、CPU/GPU 执行设计、强基线、外层/内层规模图、TSP500 因果分析、编译摊销、完整训练、最终测试质量和限制。

建议工作标题：**Scalable Population Evaluation for Automatic Algorithm Design: A GP-ACO Case Study**。

提交前逐条检查：每个“更快”是否指出比较对象和计时边界；每个“可扩展”是否指出扩展维度；每个“质量不下降”是否有预设容忍界与置信区间；每个“可泛化”是否有相应任务或硬件证据。
